# 重排连接失败：原因、最小修复与验证

## 当前结论

已按用户要求停止100题回归。原轮保存60题完整记录，061被中断且未落盘，不继续跑题、不补跑覆盖失败。

**代码中的过短连接超时已修正，但真实网络问题尚未完全解决。** 不能将本次结果交付为“重排连接已稳定修复”。

## 已确认的证据

1. 原冻结版本将HTTPX连接超时设为5秒。与Git HEAD对照，之前是30秒统一阶段超时。这是本轮修改引入的过于激进配置，不应全部归咎于外部接口。
2. 无密钥、无模型调用的同域名HTTPS探测复现：TCP约0.03秒建立，TLS握手在5秒到期抛出ConnectTimeout。失败发生在发送HTTP请求之前，没有401、403、429等响应，不能据此判为密钥、权限、额度或语义失败。
3. 恢复30秒后，三笔真实qwen3-rerank小请求中，两笔成功（约2.68秒、8.15秒），一笔仍连续两次连接超时（每次约30秒）。说明仅延长超时不能消除底层间歇问题。
4. 另一组共4次无密钥HTTPS探测：同一客户端第一次TLS握手15秒超时，第二次新握手约1秒成功，随后两次复用连接分别约0.86秒、0.39秒收到响应。根路径返回404仅证明HTTPS可达，不证明重排推理权限或长期稳定。
5. 本机存在FlClash、FlClashCore、FlClashHelperService进程，域名maas.qianwenaiapi.com解析为28.0.0.72。HTTP代理相关环境变量未设置，Windows ProxyEnable=0；这不能排除TUN/透明转发。代理/隧道路径是待验证假设，不是已证实根因。

## 修改了什么

- `rag-customer-service/src/rag_customer_service/rerank.py`：只将`connect=5.0`恢复为`connect=30.0`。
- 读取超时仍20秒，写入及连接池等待仍5秒。最多一次瞬时错误重试，认证失败不重试；不关闭证书验证、不无限等待、不编造重排结果。
- 代价：持续断连时，等待时间比5秒配置更长；这是分阶段超时，不是严格端到端总时限。
- `tests/test_rerank.py`：新增慢握手容忍测试和持续连接失败有界退出测试。慢握手测试通过外部传输边界模拟8秒所需预算，不等同真实网络8秒测量；真实连接验证独立记录。
- `evaluation/probe_rerank_connection.py`：三笔两条合成文本的小请求验证，不读取或发送知识库文档，不运行聊天模型，也不属于100题回归。结果见[smoke.json](smoke.json)。
- 未修改API Key、模型、接口地址、系统代理、知识库、阈值或语义判断标准。未加入连接池生命周期改造；复用连接可减少握手次数，但不能保证首次连接成功，不以此替代网络根因排查。
