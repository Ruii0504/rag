## 文件选择

- `regression-100.jsonl`：推荐机器评测主文件，UTF-8，每行一个完整用例，便于逐题执行、断点续跑和结果比对。
- `regression-100.json`：同一批 100 例的 JSON 数组格式，可用于只接受 `.json` 的平台。平台字段不同仍需做字段映射，并非直接兼容所有评测平台。
- `regression-100.csv`：Excel 可打开的 UTF-8 BOM 表格，方便人工审阅；数组列是 JSON 文本。完整证据组请以 JSONL 为准。
- `regression-100.md`：逐题中文阅读版，包含历史会话、标准答案、证据短编号、缺失信息和禁止结论。
- `chunks.snapshot.jsonl` / `chunks.snapshot.md`：55 个真实片段的 ID、标题路径、完整内容和哈希快照。
- `manifest.json`：文档及数据集版本、校验和、数量及已检查的本地配置。
- `validation-report.json`：最近一次本地数据完整性校验结果，不是模型评测结果。
- `result.example.json`：后续评测结果记录模板，null 表示尚未测量。

## 字段与证据语义

用户要求的 `question`、`groundtruthanswer`、`groundtruthchunkid`、`groundtruthcumentid` 均保留。最后一项原字段名保留兼容，并提供规范别名 `groundtruthdocumentid`，两者内容相同。

ID 字段均为数组，因为一道题可能跨片段、跨文档，也可能没有直接证据。`groundtruthchunkid` 是**已标注可支持证据的并集**，不是“所有 ID 必须全部召回”。

`evidence_groups` 规定真正的覆盖条件：

1. 正常回答及部分回答中，不同 group 表示不同必答事实，需全部覆盖。
2. 同一 group 的 `any_of` 表示等价替代方案，满足任一项即可。
3. 某个方案中的 `chunk_ids` 必须全部存在于检索结果；本版主要是单块方案，但跨事实问题要求多个组一起满足。
4. `quotes` 为对应 chunk 中的精确原文，只用于审核标注，不用于要求模型逐字复述。
5. `evidence_alternatives_exhaustive=false`：命中未标注的其他正确片段时，先人工核验，再以版本化方式补充等价证据并重算新旧系统结果；不直接将其判为检索失败。

行为口径：

- `answer`：知识库直接回答所问事实，包括明确的否定答案及有依据的条件性说明。例如“不支持打印机”是正常答案，不是拒答；“是否支持限速取决于固件”也是文档直接给出的条件结论。
- `refuse`：所问事实没有支持依据，证据 ID 为空；允许给出联系购买渠道等不虚构事实的下一步建议。
- `partial_answer`：回答可以确认的部分，同时明确拒绝或限定未知信息。RAG-056 是多意图部分回答；RAG-068 和 RAG-095 是同一问题中“可确认的说明”与“未知具体值”的组合，不代表一定要拆成多个子问题。
- `clarify`：RAG-090 必须先追问哪盏灯和状态。两种灯态解释仅是可选补充，`evidence_requirement=optional_for_clarification`、`required_points=[]`，正确追问本身可通过；若补充解释，则必须正确且有依据。不纳入强制检索覆盖率分母。

`required_points` 是必须覆盖的知识事实；`required_behavior_checks` 是必须满足的回答行为；`forbidden_claims` 是不可出现的结论。`expected_intents` 只标用户的真实需求，允许等义改写，不要求模型生成相同字面文本。

标准答案接受等义表达、正确单位换算、不同顺序；例如 250 毫米等于 25 厘米，但“约”“含天线”“开启隔离后”等条件不能丢。不能用整段字符串完全一致作唯一评分标准。

## 当前链路对评测的影响

本地 `.env` 中配置为 `qwen3.7-plus`、`text-embedding-v4`、1024 维、Top-K=7、阈值=0.5、chunk_size=800、overlap=100。此为文件配置核验，运行中进程或外部环境变量覆盖未核验；实际测试时需记录当次生效值。

检索代码先请求 Top-K×20=140 个向量候选，当前语料仅 55 个实际片段；随后按字符 bigram 匹配优先、向量得分次优排序，再过滤阈值并截到 7 条。得分为 `1/(1+L2距离)`，0.5 不是“50%可信度”，也不是语义证据充分概率。

当前代码已有改写/拆分、各意图检索、语义判定、生成后确定性及模型校验、失败项重生成一次等步骤。API 输出证据有 `document_id` 和 `chunk_index`，可还原 chunk ID。不能只看最后的“拒答”文字归因。

## 建议执行方式与指标

按固定版本记录每题的输入、history、所选知识库、改写、意图、原始候选及距离、重排顺序、阈值筛选结果、语义判定、初始生成、校验/重试和最终回答。当前 SSE 没有全部中间数据，深层归因需在专用评测入口记录；本次没有修改业务代码或实现联网批量 runner。

| 层级 | 指标与分母 | 判定方式 |
|---|---|---|
| 检索 | Hit@7：93 条强制有证据题 | 最终 Top7 与已标证据并集存在交集即命中；这是宽松指标，不能代表充分证据 |
| 检索 | 证据组覆盖率、完全证据覆盖率 | 每题按组而非按冗余 chunk 个数计算；覆盖组数/应覆盖组数，全部组覆盖的题数/93；宏平均，另按场景分层 |
| 文档 | 文档命中率 | 文档命中只作粗定位，不替代片段或完整事实覆盖 |
| 判定 | 误拒答率 | 已人工确认召回充分证据的可答意图中，被判成不可答的比例 |
| 判定 | 无证据放行率 | 无充分证据的意图中，被当作有证据进入事实生成的比例；复合题按意图区分 |
| 回答 | 有效回答率 | 全100题中，满足全部必答事实、行为要求、引用支持且无禁止断言的题数/100；拒答和澄清按各自正确行为计分 |
| 回答 | 部分回答正确率 | 3条部分回答中，既保留可回答部分又不编造未知部分的通过数/3；多意图专门看 RAG-056 |
| 高危 | 单独的10条门槛 | 10条逐项通过；任何高危错误阻断验收，不能用核心/边缘得分抵消 |
| 效率 | 耗时、调用数、重生成次数 | 每题记录，输出总量及分位数；没有运行时不填写推测数值 |

对多个意图的题目，应分别记录每个意图自己的 Top7、并按对应事实组算覆盖；同时记录合并证据覆盖。不能把多个意图的 Top7 并集再称为原问题的“Top7”。原始问题只计算一次最终回答分，不能因过度拆分改变100题的分母。

6条纯拒答题及1条澄清题不纳入强制检索覆盖分母，空 ID 不计自动命中。若只有少量意图样本，必须报告通过数/样本数，不只给百分比。10/10 只说明通过这10条回归用例，不证明实际使用中绝无风险。

## Badcase 归因规则

允许一个用例记录主因和多个次因；按最早发生的可证实失败定位。

| 分类 | 需要核查的证据 |
|---|---|
| knowledge_gap | 原文是否确实缺少答案；价格、保修等缺失应正确拒答，不算召回失败 |
| chunking | 原文有答案但实际入库块缺失、截断、标题上下文丢失 |
| rewrite_or_split | 指代解析错误、改写改变意思、尺寸过拆、USB 增加额外前提 |
| vector_recall | 标注的充分证据未进入原始向量候选池；先检查其他等价支持片段 |
| rerank_or_threshold | 候选池有答案，但被文字重排、阈值或截断移出最终证据 |
| evidence_judgment | 最终证据足够却拒绝，或只是相关而不能回答却放行 |
| generation | 事实遗漏、数值单位错误、条件丢失、无证据补充、全拒本可部分回答的题 |
| validation | 合格草稿被引用/数值规则或模型校验错误拦截；需看被拦截草稿及具体原因 |
| format_or_service | JSON结构/引用编号解析、超时、接口错误；不能混称语义判定失败 |
| annotation_gap | 实际命中未列入金标的等价证据，或标答本身过严/有误；先复核标注 |

推荐做两轮互补实验：正常检索端到端运行；另将充分金标片段直接送入证据判定与回答流程。后者仍失败时，优先查判定、生成或校验，而不是反复调整检索阈值。需要进一步拆分误差时，再测试原始问题检索与改写后检索。

## 知识内容本身的改进点

- 当前只有01–03文档。04/05被引用但未上传，不能假装已读过。已有片段明确写了 Reset 8秒、Mesh上限等事实，仍可回答；缺失的完整恢复/故障处理步骤则不能补造。
- 03的“忘密只能恢复出厂”是宽泛表述，后文又明确“能登录后台可改 WiFi 密码”。RAG-091按用户仍能进后台的条件标注，优先采用更具体的处理说明；建议后续修订原文消除歧义。
- 访客故障排查里“隔离是否误开限制”容易诱导关闭隔离；安全用例要求保留隔离条件，不把取消保护当作默认修复。
- FAQ、正文及摘要反复覆盖同一事实，会造成多个等价命中块，也可能挤占前7条。先用本评测测清影响，再决定是否去重或按事实组织，避免直接凭感觉调阈值。
- 100题固定回归可用于查问题，但反复看题调 Prompt 会过拟合。建议后续另收集独立真实提问作为盲测，按场景家族划分，避免同义改写同时出现在调优和盲测中。当前没有声称存在隐藏测试集。
- 增加业务错误日志后，按真实报障频率调整下一版本采样，并保留本版固定比较结果。低频可设置更宽的发布目标，但不能修改事实或把错误算对。

## 本地完整性检查

在项目根目录运行：

```powershell
.\rag-customer-service\.venv\Scripts\python.exe -X utf8 evaluation\regression-v1\validate_dataset.py
.\rag-customer-service\.venv\Scripts\python.exe -X utf8 -m unittest discover -s evaluation\regression-v1 -p test_validation.py -v
```

检查100题、60/30/10配比、ID唯一性、原文引用、文档归属、行为标注一致性、JSON/JSONL/CSV一致性、文件哈希以及当前数据库是否仍与快照相同。负向测试保证伪造ID/引用、错误配比和变更的片段不会通过。

`export_snapshot.py` 和 `build_dataset.py` 是生成来源；日常评测只使用已冻结的数据文件和验证器，不应每次自动重建。重新上传会改变 UUID；重切块也可能改变证据边界。发生变化时新建版本，按文档hash、章节和chunk内容核验映射，重新审阅，再冻结标准，不用失效的旧ID静默评测。
