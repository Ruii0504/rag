## 2. 产品概述

### 2.1 项目背景

企业内部的产品资料通常分散在多份文档中。客服人员面对产品规格、安装配置、故障排查和售后政策等问题时，需要人工查找资料，回答效率和一致性容易受到个人经验影响。

通用大模型虽然能够生成自然语言回答，但可能使用自身知识补充产品事实，造成无依据回答。为降低这一风险，本项目建设一个本地运行的 RAG 智能客服系统：管理员先将产品 Markdown 文档整理为知识库；客服人员提问时，系统必须先检索知识库，再根据检索证据回答，并展示证据来源。证据不足时，系统明确拒绝回答。

### 2.2 产品定位

本产品是供内部单实例使用的知识库问答原型，用于学习和验证以下能力：

- 管理 Markdown 产品知识；
- 在一个或多个知识库中按语义检索资料；
- 基于检索证据生成客服回答；
- 展示问题改写、检索、证据判定和回答过程；
- 通过明确拒答降低无依据回答风险。

本产品不是面向大规模生产客服中心的完整运营平台。

### 2.3 核心价值

- **提高查找效率**：客服人员不必逐份翻阅产品文档。
- **统一回答依据**：回答只使用已上传的知识库内容。
- **降低错误风险**：证据不足时拒答，不允许模型凭常识补充产品事实。
- **增强可追溯性**：回答同时展示来源文档、章节、相似度和文本片段。
- **便于学习验证**：用户能够看到系统从问题改写到最终回答的完整过程。

## 3. 产品目标与成功指标

### 3.1 产品目标

1. 用户可以在图形界面中完成知识库和 Markdown 文档的完整生命周期管理。
2. 用户可以选择一个或多个知识库进行多轮问答。
3. 系统每次回答前都必须执行检索，并根据证据充分程度决定回答或拒答。
4. 所有有依据的回答都能追溯到具体文档和章节。
5. 文档或知识库删除后，相关内容不能继续被检索或引用。
6. 页面能够展示处理进度、检索过程、证据和流式回答。

### 3.2 可测试的成功指标

| 指标 | 目标 |
| --- | --- |
| 产品资料摄取 | 现有 6 份产品 Markdown 文档全部能够成功摄取 |
| 重复内容控制 | 同一知识库中的相同内容 100% 被拦截；不同知识库允许保存相同内容 |
| 检索范围隔离 | 所有检索结果均来自用户当前选择的知识库，不得泄漏未选知识库内容 |
| 强制检索 | 每次有效提问均执行一次检索，不由模型自行决定是否检索 |
| 证据引用 | 所有被系统回答的问题均展示来源文档、章节和证据片段 |
| 知识库外问题 | 最小评测集中至少 3 个知识库外问题全部拒答，不使用模型常识作答 |
| 多轮问答 | 最小评测集中至少 2 个指代型追问均能结合当前会话历史完成问题改写并检索到正确资料 |
| 删除一致性 | 删除文档或知识库后，本地文件、元数据和向量数据中的相关内容均无残留且不可召回 |
| 评测覆盖 | 建立不少于 12 个固定评测问题，覆盖产品规格、联网、WiFi、Mesh、恢复出厂、故障和保修等场景 |
| 自动化验证 | 所有核心自动化测试通过，真实模型连通性检查与离线测试分开执行 |
| 密钥安全 | 真实 API Key 不进入源码、日志或 Git 版本记录 |

## 4. 目标用户与使用场景

### 4.1 用户角色

#### 知识库管理员

负责创建知识库、上传产品资料、检查处理结果，以及删除失效文档或知识库。

#### 客服人员

负责选择与当前业务相关的知识库，提出客户问题，查看回答、执行过程和引用证据。

两个角色仅用于描述不同的使用目标。MVP 不实现账号登录、角色权限或页面访问隔离，同一内部用户可以操作全部页面。

### 4.2 核心使用场景

1. 管理员创建“路由器产品知识”知识库并上传产品说明文档。
2. 管理员重复上传同一内容时，系统在产生模型费用前明确阻止重复入库。
3. 客服人员选择一个或多个知识库，询问产品安装、配置或故障问题。
4. 客服人员提出“这样会清空设置吗？”等追问，系统结合当前对话理解指代对象。
5. 客服人员查看回答所依据的文档、章节、相似度和原文片段。
6. 客服人员询问天气等知识库外问题时，系统完成检索后明确拒答。
7. 管理员删除过期文档后，客服人员不能再次检索到该文档内容。

### 5.2 明确不做

- 用户登录、角色权限、多租户和数据隔离；
- 面向公网或大规模客服团队的部署；
- 对话历史长期保存、搜索或运营分析；
- PDF、Word、网页等非 Markdown 数据源；
- 后台异步任务、任务队列和分布式处理；
- 混合检索、重排序器和知识图谱；
- 多模型动态切换；
- 独立 API 服务或另一套前端框架；
- 人工客服转接、工单、满意度评价和客服运营报表。

## 6. 功能需求

### 6.1 应用首页

#### 功能说明

首页帮助用户理解系统用途和当前运行条件，并提供知识库管理页和智能客服页的入口。

#### 需求规则

- 展示产品用途和两个核心页面的说明；
- 展示当前聊天模型和 Embedding 模型名称；
- 展示配置是否完整，但不得显示 API Key；
- 配置缺失时明确提示用户完成本地环境配置；
- 首页不承担知识库管理或客服问答业务操作。

### 6.2 知识库管理

#### 创建与列表

- 用户可以输入名称创建知识库；
- 知识库名称不得重复；
- 创建完成后列表立即显示新知识库；
- 用户可以从列表中明确选择当前知识库；
- 未选择知识库时，不得执行文档上传或误删操作。

#### 删除知识库

- 删除前必须展示确认步骤；
- 确认对象必须是用户明确选择的知识库；
- 删除完成后，该知识库的文档、原文件、元数据和向量块必须全部删除；
- 删除一个知识库不得影响其他知识库；
- 删除后页面立即刷新列表和当前选择状态。

### 6.3 文档管理

#### 上传限制

- 只接受扩展名为 `.md` 的 UTF-8 Markdown 文档；
- 空文档、无法解码的文档和非 Markdown 文件必须在向量化前被拒绝；
- 支持一次选择并上传多份 Markdown 文档；
- 上传处理为同步流程，页面需持续展示当前进度。

#### 文档处理

系统按以下产品流程处理每份文档：

1. 校验格式和内容；
2. 统一换行等文本格式；
3. 计算规范化内容的唯一指纹；
4. 检查当前知识库中是否存在相同内容；
5. 按 Markdown 标题切分章节；
6. 将超长章节继续拆成适合检索的文本片段；
7. 批量生成语义向量；
8. 保存原文、检索数据和文档记录；
9. 向页面报告完成结果和文本块数量。

#### 重复文档规则

- 同一知识库中，规范化后内容相同的文档视为重复；
- 文档仅换行风格不同时，仍视为相同内容；
- 不同知识库允许保存相同内容；
- 重复检查必须发生在调用 Embedding 模型之前，以避免无效费用。

#### 文档列表与删除

- 文档列表至少展示原文件名、处理状态、文本块数量和上传时间；
- 删除文档前必须明确确认；
- 删除完成后，原文件、文档记录和所有向量块均不得残留；
- 删除一份文档不得影响同知识库或其他知识库中的其他文档。

#### 失败处理

- 页面至少区分重复文档、空文档、格式错误、编码错误和模型调用失败；
- 任一步失败时，系统应清理本次处理已经产生的文件、向量和元数据；
- 清理失败时保留原始错误，并展示不包含密钥的安全提示；
- 失败文档不得以成功状态出现在列表中，也不得被检索到。

### 6.4 多知识库检索

#### 检索范围

- 客服人员可以选择一个或多个知识库；
- 未选择知识库时，页面应阻止提问或返回明确说明；
- 系统内部使用稳定的知识库 ID 限制检索范围，不依赖可修改的显示名称；
- 检索结果不得包含任何未选择知识库的内容。

#### 检索和证据筛选

- 每次有效问题都必须生成查询向量并执行检索；
- 系统按照相关程度统一排序候选文本片段；
- 最多保留配置指定的 Top-K 条候选结果；
- 低于相似度阈值的结果不得作为回答证据；
- 全部候选结果被过滤时，系统判定证据不足；
- 每条有效证据应具有稳定编号，供回答引用。

### 6.5 智能客服问答

#### 固定处理流程

每次问题均按照以下顺序执行：

1. 使用当前会话历史将问题改写为可独立理解的问题；
2. 在用户选择的知识库中执行检索；
3. 根据 Top-K 和相似度阈值判断证据是否充分；
4. 证据充分时，根据编号证据生成回答；
5. 证据不足时，使用固定中文话术拒答；
6. 输出完成状态或安全错误状态。

模型不得跳过检索，也不得自行选择其他工具或自由改变处理流程。

#### 回答规则

- 回答只能使用当前检索得到的编号证据；
- 回答不得加入证据之外的产品事实；
- 回答正文应引用相应证据编号；
- 回答以流式方式逐步显示；
- 最终完整回答保存到当前页面会话中；
- 证据不足时不得调用答案生成模型补充常识。

#### 拒答规则

- 未选择知识库时，说明需要先选择知识库；
- 未检索到充分证据时，明确说明当前资料不足；
- 知识库外问题也必须完成检索后拒答；
- 拒答仍需保留检索过程，便于用户理解原因。

### 6.6 多轮会话

- 当前会话保存用户消息和最终助手消息；
- 问题改写可使用当前会话历史解决“这样”“它”等指代；
- 刷新页面、关闭会话或服务重启后不恢复历史；
- 对话历史不得写入 SQLite 或其他长期存储；
- 无历史且问题可以独立理解时，改写不得改变原意。

### 6.7 执行过程和证据展示

页面按实际发生顺序展示以下信息：

- 问题改写开始和完成；
- 检索开始及当前启用的知识库；
- 检索命中数量；
- 证据判定结果；
- 回答增量或拒答内容；
- 完成或错误状态。

每条证据至少展示：

- 来源文档名称；
- Markdown 标题路径；
- 相似度；
- 相关文本片段。

### 6.8 Figma UI 微调与回写

#### 功能原型进入 Figma

- P0 功能原型完成后，将首页、知识库管理页和智能客服页写入同一个 Figma Design 文件；
- 保留已确认的信息结构、业务流程和交互限制；
- 覆盖首页默认态，知识库空态、列表态、上传态、错误态和删除确认态，以及客服空态、检索态、流式回答态、完成态、证据不足态和错误态；
- 重复页面元素应使用可复用组件或实例。

#### 用户批准和设计冻结

- 用户可在 Figma 或 Codex Figma 插件中调整视觉、布局和信息层级；
- UI 微调不得新增业务流程、接口、持久化需求或 Streamlit 无法合理实现的能力；
- 用户批准后，交接文档记录同一 Figma 文件中各批准节点的名称、节点链接、对应状态和批准日期。

#### 回写 Streamlit

- 实现以批准节点的设计上下文和截图为准；
- 优先使用 Streamlit 主题和原生组件，仅在必要处使用少量局部 CSS；
- 不引入 React、Tailwind 或另一套前端运行时；
- UI 修改不得改变知识库生命周期、强制检索、事件顺序、拒答逻辑和会话历史范围；
- 回写后需同时完成视觉核对和业务回归验收。

## 7. 页面结构与交互状态

### 7.1 页面结构

```text
RAG 智能客服系统
├── 首页
├── 知识库管理
│   ├── 知识库列表与选择
│   ├── 新建与删除知识库
│   ├── Markdown 文档上传
│   └── 文档列表与删除
└── 智能客服对话
    ├── 多知识库选择
    ├── 当前会话消息
    ├── Agent 执行过程
    ├── 检索证据
    └── 流式回答或拒答
```

### 7.2 关键交互状态

| 页面 | 状态 | 用户可见反馈 |
| --- | --- | --- |
| 首页 | 配置正常 | 显示模型名称和可用状态 |
| 首页 | 配置缺失 | 显示缺失配置提示，不展示敏感值 |
| 知识库管理 | 空列表 | 引导用户创建第一个知识库 |
| 知识库管理 | 已有知识库 | 显示列表、当前选择和文档操作区 |
| 知识库管理 | 上传处理中 | 显示校验、切分、向量化、保存和完成进度 |
| 知识库管理 | 文档失败 | 显示可理解的错误类型和安全信息 |
| 知识库管理 | 删除确认 | 明确展示即将删除的知识库或文档 |
| 智能客服 | 未选择知识库 | 禁用或拒绝提问，并说明原因 |
| 智能客服 | 空会话 | 展示输入入口和知识库选择状态 |
| 智能客服 | 检索中 | 展示问题改写、知识库范围和检索状态 |
| 智能客服 | 流式回答 | 在同一回答区域持续追加文本 |
| 智能客服 | 回答完成 | 展示完整回答和编号证据 |
| 智能客服 | 证据不足 | 展示固定拒答和检索过程 |
| 智能客服 | 安全错误 | 展示不含密钥或完整提示词的简短信息 |

### 7.3 删除交互原则

- 所有删除操作必须由用户明确选择对象并确认；
- 页面不得根据上传文件名推断真实删除目标；
- 删除成功后立即刷新列表和选择状态；
- 删除失败时不得错误显示为成功。

## 8. 数据要求

### 8.1 核心业务数据

| 数据对象 | 必要信息 | 用途 |
| --- | --- | --- |
| 知识库 | 唯一 ID、名称、创建时间 | 管理资料范围和检索过滤 |
| 文档 | 唯一 ID、知识库 ID、原文件名、内容指纹、状态、文本块数量、上传时间 | 文档列表、去重和生命周期管理 |
| 文本块 | 知识库 ID、文档 ID、文档名、标题路径、稳定序号、内容指纹、正文 | 语义检索和证据引用 |
| 证据 | 编号、来源文档、标题路径、相似度、文本片段 | 证据判定、回答引用和页面展示 |
| 会话消息 | 用户问题、最终助手回答 | 当前会话中的多轮问题改写 |
| 执行事件 | 事件类型、状态和安全展示内容 | 页面按顺序展示 Agent 过程 |

### 8.2 数据存储规则

- SQLite 保存知识库和文档元数据；
- Chroma 的单一 collection 保存所有知识库的向量块，并通过知识库 ID 过滤；
- 本地文件目录保存原始 Markdown 文档；
- 同一 collection 中的向量必须来自同一个 Embedding 模型和相同维度；
- 更换 Embedding 模型或维度后，必须清空并重建全部向量；
- 会话消息只存在当前 Streamlit 会话中，不持久化。

### 8.3 数据一致性

- 文档成功状态必须意味着原文件、文档记录和向量数据均已保存；
- 文档失败状态不得留下可检索向量或成功元数据；
- 删除成功必须意味着相关文件、元数据和向量均已删除；
- 不同知识库的数据不得在检索和删除过程中相互影响。

## 9. 非功能性需求

### 9.1 运行环境

- 使用 Python 3.12；
- 以本地单进程、单实例方式运行；
- 适用于少量并发和最多数万文本块；
- 页面使用 Streamlit，不额外建设独立 Web API 服务。

### 9.2 可用性

- 核心操作均可通过页面完成，无需用户使用命令行管理知识库；
- 上传等耗时操作必须展示进度，避免页面无反馈；
- 回答以流式方式显示；
- 错误信息使用明确中文，区分用户输入错误与模型或系统错误；
- 删除操作必须确认，降低误操作风险。

### 9.3 性能与容量

- 检索只在用户选择的知识库范围内执行；
- 文档向量应批量生成，避免逐块产生不必要请求；
- Streamlit 脚本重跑时应复用数据库、向量库和模型客户端等资源；
- MVP 不承诺大规模并发或生产级服务可用性指标；
- 实际模型响应速度受本地网络和千问服务影响，验收重点是过程持续可见且页面不会静默等待。

### 9.4 安全与隐私

- 千问 API Key 只能从本地环境变量读取；
- API Key 不得出现在源码、示例配置值、页面、测试输出、日志或 Git 中；
- 页面错误不得泄漏 API Key、完整提示词或底层敏感对象；
- 用户上传文件名不得直接决定真实存储和删除路径。

### 9.5 可维护性与验证

- 页面只负责交互展示，不直接处理数据库和向量库细节；
- 知识库、文档处理、检索和问答流程具有明确职责边界；
- 关键业务链路均应有离线自动化测试；
- 真实千问连通性检查与日常自动化测试分开，避免测试产生持续费用；
- 新开发者应能够仅根据 README 从空数据目录启动并复现验收流程。

## 10. 异常与边界场景

| 场景 | 预期行为 |
| --- | --- |
| 未配置 API Key | 启动或首页明确提示配置错误，不延迟到首次模型调用才发现 |
| 上传非 Markdown 文件 | 在向量化前拒绝并说明仅支持 `.md` |
| 上传空文档 | 在向量化前拒绝并说明内容为空 |
| 上传非 UTF-8 文档 | 在向量化前拒绝并说明编码不符合要求 |
| 同库重复内容 | 在向量化前阻止上传，不产生模型费用 |
| 不同库相同内容 | 允许分别保存和检索 |
| Embedding 调用失败 | 清理本次产生的数据并展示安全错误 |
| 文件、向量或元数据写入失败 | 按已完成步骤逆序清理，不产生半完成文档 |
| 未选择知识库 | 阻止提问或返回明确拒绝原因 |
| 检索无有效证据 | 展示固定拒答，不调用回答生成补充常识 |
| 知识库外问题 | 仍执行检索，然后因证据不足拒答 |
| 流式回答中发生错误 | 结束当前回答并展示安全错误，不伪装为成功 |
| 删除单文档 | 仅删除目标文档的文件、元数据和向量 |
| 删除知识库 | 删除目标知识库全部数据，其他知识库不受影响 |
| Embedding 模型或维度变化 | 拒绝复用旧 collection，并提示重建全部向量 |
| 页面刷新或服务重启 | 当前对话历史丢失，知识库和文档数据保留 |

## 11. 用户故事与验收标准

### US-01 创建知识库

**作为**知识库管理员，**我希望**创建并查看知识库，**以便**按产品或业务范围管理资料。

验收标准：

- 输入有效且未重复的名称后创建成功；
- 列表立即显示新知识库；
- 重复名称被明确拒绝；
- 未创建知识库时展示空状态引导。

### US-02 上传产品资料

**作为**知识库管理员，**我希望**上传 Markdown 产品文档并看到处理进度，**以便**将资料转成可检索知识。

验收标准：

- 只接受 UTF-8 `.md` 文件；
- 页面依次展示校验、切分、向量化、保存和完成状态；
- 成功后列表显示文件名、文本块数量和上传时间；
- 现有 6 份产品文档可以全部摄取。

### US-03 阻止重复资料

**作为**知识库管理员，**我希望**系统识别重复内容，**以便**避免重复知识和无效模型费用。

验收标准：

- 同一知识库的相同内容在向量化前被拦截；
- 仅换行风格不同的内容仍被识别为重复；
- 不同知识库允许保存相同内容。

### US-04 删除资料

**作为**知识库管理员，**我希望**删除过期文档或整个知识库，**以便**确保客服只使用有效资料。

验收标准：

- 删除前必须确认目标；
- 删除文档后，其文件、元数据和向量块均不存在；
- 删除知识库后，其全部数据均不存在；
- 被删除内容无法再次召回；
- 其他知识库和文档不受影响。

### US-05 选择多个知识库问答

**作为**客服人员，**我希望**选择一个或多个知识库提问，**以便**在正确的资料范围内获得回答。

验收标准：

- 未选择知识库时无法正常提交问题，并看到原因；
- 选择一个知识库时不返回其他知识库内容；
- 选择多个知识库时，结果统一按相关程度排序；
- 每次有效问题都执行一次检索。

### US-06 获得有依据的回答

**作为**客服人员，**我希望**回答附带来源，**以便**核对内容并向客户提供可信信息。

验收标准：

- 有充分证据时回答逐步显示；
- 回答正文引用证据编号；
- 证据展示文档名、章节、相似度和文本片段；
- 回答不包含证据之外的产品事实。

### US-07 获得安全拒答

**作为**客服人员，**我希望**资料不足时系统明确拒答，**以便**避免向客户传递未经证实的信息。

验收标准：

- 所有候选证据低于阈值时使用固定中文话术拒答；
- 拒答路径不调用回答生成补充常识；
- 知识库外评测问题全部拒答；
- 页面仍显示检索过程和证据判定结果。

### US-08 进行多轮追问

**作为**客服人员，**我希望**系统理解当前会话中的指代，**以便**自然地连续追问。

验收标准：

- 系统结合当前会话历史改写指代型问题；
- “如何恢复出厂设置？”后的“这样会清空原来的网络设置吗？”能够检索到相关维护资料；
- 无历史且问题独立时不改变问题原意；
- 页面刷新或服务重启后不恢复历史。

### US-09 查看执行过程

**作为**客服人员，**我希望**看到系统如何处理问题，**以便**理解回答或拒答的原因。

验收标准：

- 页面按顺序展示问题改写、检索、证据、判定和回答状态；
- 事件顺序与实际执行顺序一致；
- 错误事件不包含 API Key 或完整提示词。

### US-10 获得一致的 UI

**作为**内部用户，**我希望**三个页面具有一致且清晰的视觉层级，**以便**快速理解操作和系统状态。

验收标准：

- 首页、知识库页和客服页的关键状态均在同一 Figma 文件中形成可定位节点；
- 用户明确批准节点级 UI 基线；
- 最终 Streamlit 页面与批准节点完成逐状态比对；
- UI 回写后全部核心行为验收仍通过。

## 12. 验收方案

### 12.1 自动化验收

自动化测试至少覆盖：

- 配置缺失与正确解析；
- 知识库、文档、文件和元数据操作；
- Markdown 校验、规范化、哈希和标题感知切分；
- 千问客户端的离线协议适配；
- 多知识库向量过滤、查询和删除；
- 摄取失败后的数据清理；
- Top-K、相似度阈值和证据判定；
- Agent 固定分支、检索次数和事件顺序；
- 依赖组合和资源复用。

### 12.2 最小问答评测集

评测集不少于 12 个问题，并满足：

- 产品规格、首次联网、WiFi 修改、Mesh、恢复出厂、指示灯故障和保修各至少 1 题；
- 多轮指代追问至少 2 题；
- 知识库外问题至少 3 题；
- 每题记录预期命中文档和预期回答或拒答结果；
- 使用同一评测集比较少量 Top-K 和阈值配置；
- 采用能够覆盖应回答问题且让所有越界问题拒答的最简单配置。

### 12.3 端到端验收

从空数据目录启动后，依次验证：

1. 完成本地配置并启动应用；
2. 创建知识库；
3. 上传 6 份产品 Markdown 文档并查看进度；
4. 重复上传同一文档并确认被拦截；
5. 删除单份文档并验证零残留；
6. 选择单个和多个知识库检索；
7. 完成单轮问答和多轮指代追问；
8. 核对回答中的证据引用；
9. 使用知识库外问题验证拒答；
10. 删除知识库并验证全部相关数据消失；
11. 核对批准的 Figma 节点与最终页面关键状态；
12. 确认 API Key 和运行数据未被 Git 跟踪。

## 14. 风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 检索阈值过低 | 知识库外问题可能获得错误回答 | 使用固定评测集调优阈值，并要求证据不足时拒答 |
| 检索阈值过高 | 产品问题可能频繁拒答 | 对应回答问题记录预期文档，用相同评测集平衡召回和拒答 |
| 文档质量不一致 | 切分和检索效果下降 | 仅接受 UTF-8 Markdown，按标题切分并保留标题路径 |
| Embedding 模型变更 | 新旧向量不兼容 | 保存模型与维度信息，变更后强制重建向量 |
| 外部模型或网络失败 | 上传或回答中断 | 展示安全错误，清理半成品，真实连通性检查与单元测试分开 |
| 删除流程不完整 | 过期资料仍可能被召回 | 对文件、SQLite 和 Chroma 三层数据执行一致性验收 |
| 模型越过证据回答 | 产生无依据产品事实 | 固定流程、强制检索、编号证据提示和证据不足拒答 |
| UI 设计超出 Streamlit 能力 | 回写成本增加或被迫引入新框架 | Figma 冻结前执行可实现性复核，限制为原生组件、主题和少量 CSS |
| PRD 与实施细节混杂 | 产品需求难以维护 | PRD 说明产品行为和验收口径，具体文件及编码步骤继续由实施计划维护 |

## 15. 产品约束与后续方向

### 15.1 当前约束

- 仅适用于内部单机、小规模试用；
- 只支持 Markdown；
- 依赖千问官方 OpenAI 兼容接口；
- 对话历史仅在当前页面会话中有效；
- 不具备生产级权限、审计、监控和高可用能力；
- 语义检索效果依赖文档质量、Embedding 模型和阈值配置。

### 15.2 后续方向评估原则

MVP 验收完成后，可根据真实试用结果评估是否增加其他文档格式、权限、长期会话、运营统计、混合检索、重排序或独立服务。上述能力均不属于当前承诺范围，只有在明确用户价值、数据规模和验收指标后才能进入下一版本需求。
